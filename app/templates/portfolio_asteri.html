01 / The problem

Build the store.
Support the operation.

The storefront needs to help a customer find products, explore combinations and manage a cart or account. The maker needs a separate place to manage products, inventory and orders.

Those interfaces also depend on identity, permissions, protected checkout operations and a deployment that can be checked. The project brings those parts together while keeping customer and administrative responsibilities clear.

These are product goals supported by the implementation. Customer research, sales growth and conversion impact were not measured in this case study.

03 / Engineering decisions

Make the boundaries
visible and testable.

Package a known runtime.

Multi-stage Docker builds separate building from running. The runtime uses a non-root user, read-only filesystems and bounded resources. Runtime secrets remain outside the built image.

Tradeoff: a shared tested image simplifies release identity across services, while increasing what that image contains.

Configure the proxy explicitly.

Routing and HTTPS configuration identify which service handles customer and administrative traffic. Persistent certificate state supports container recreation.

Tradeoff: explicit configuration takes more maintenance, but avoids granting the proxy access to the Docker socket.

Verify sensitive actions on the server.

Protected APIs check identity and permissions. Checkout derives prices and stock from authoritative data and uses transactions for reservations.

Reason: browser input can request an action; it cannot decide the trusted price, inventory state or authorization outcome.

04 / The release challenge

Prove which version
reaches the server.

A successful build does not establish that the running service uses the same image or source revision. The delivery process needs an explicit link between the checked source, the tested image and the accepted deployment.

The standalone release gate runs the complete build/test workflow and produces signed evidence. Publication and deployment are separate steps.

  1. 01

    Check committed source.

    Run the application and policy checks against the intended source revision.

  2. 02

    Build and inspect the image.

    Build the production image, test its runtime behavior and scan the intended artifact.

  3. 03

    Verify the published identity.

    Publish the image and pull back its immutable digest to confirm the artifact being delivered.

  4. 04

    Sign the passed checklist.

    Bind the proof to the exact image, source revision and reviewed release policy.

  5. 05

    Verify before deployment.

    The server checks the proof before changing the release, followed by HTTPS revision checks.
